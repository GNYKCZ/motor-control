# 固定零矢量诊断记录方案

本批用户授权：2026-10-31，允许沿一次烧录收集配置、引脚、原始采样与停机恢复证据方向准备软件。未授权自动烧录或启动电机。

阶段成果：同一固件输出一份有限、可校验、可判定完整性的诊断记录。不能承诺一次实验区分功率桥实际电压与模拟放大器误差。

## 既定输出契约

保留三相CCR=900/900/900、PI不提交输出、原截止时间和保护门限、PA12每次启动一次资格。故障先关闭输出再记录，不自动重试。保持现有采零基线，不将PWM下的偏移重新采为零。不得以滤波或放宽门限获得通过。

## 实施范围

1. board_pwm拥有启动时配置快照：CR1、CR2、CCMR1/2、CCER、BDTR、PSC、ARR、RCR、CCR1/2/3、GPIOA_CRH及AFIO_MAPR。标明读取时刻、阶段和代次。CCR读数是预装值，不能标为有效比较值的直接读回。
2. ADC IRQ在原保护路径之前仅复制有界整数原始数据与时序；不得格式化、等待或计算浮点。记录样本序号、完成时间、原始U/V、编码器角度、TIM1方向及CNT、TIM2 CNT、GPIOA IDR与MOE。读取前后时标/方向用于识别跨边沿的不确定快照。快照是IRQ时刻，不冒充ADC采样孔径时刻。
3. 记录动作前有限样本、启动阶段、所有动作样本（最多20ms）、故障样本，以及停止后有限恢复样本。停止前后样本分别标注，不能混入闭环控制轨迹。恢复采样不恢复输出；缺失时必须报告不完整，不能无限等待。
4. 首次故障只冻结一次。持续故障不能清空RAM或重复安排头帧。保护关闭输出不依赖记录是否成功。
5. 配置和记录全部在停机后按有序CRC帧导出。头帧带固件版本、格式、条数、采集完成/溢出标志；末帧带实际条数。解析器拒绝缺帧、重复、错序、CRC失败，不自动补齐。
6. GPIO三位同时读取，只能表明该瞬间PA8/9/10逻辑电平；不能证明功率输出同步，也不能排除窄毛刺。第一次实现保留225us ADC相位，避免同时更改触发链路；同一固件可预留明确标识的相位对照，但未经验证不得自动轮换或故障后继续运行。

## 验证与停止点

- 检查多种提前终止：启动失败、第一采样故障、第二采样故障、正常截止、STOP、Break。证明没有延长输出、记录重复、恢复阶段重启。
- 用已知注入序列验证前/中/后段与首次故障归属，以及导出完整性。
- 校验记录快照的不确定性标签；边沿附近不同电平不得自动判为不同步故障。
- 实际Keil工程编译；记录RAM/栈预算及IRQ新增路径成本。保留用户DAP工程设置。
- 更新串口版本和main.c日期注释；版本、构建产物、固定提交绑定。独立Review后交付。
- 板端NOT RUN。新版本资料不足必须指出缺失，不宣称硬件或闭环验收。

## 现有证据

基线提交12c5302，FW1,31-22-40,DQ_VEC0。用户22:53记录cfg00040002，在输出开始后约1228us触发iq诊断，原始U2072/V2081，名义id=-13.50mA、iq=-80.06mA。CRC验证及计算见build/dq_current/user_vector_trip_20261031_2253。只含一个此前有效观测点，不能据此判定持续增长。

## 本批实现（记录功能，固件 01-00-03，板端NOT RUN）

本批按上面六项实施范围落地，仍固定三相900/900/900、PI不提交输出、20ms绝对截止与原保护门限。

1. **配置快照** `board/board_pwm.c`：`record_config` 在四个明确阶段读取 TIM1 的
   CR1/CR2/CCMR1/CCMR2/CCER/BDTR/PSC/ARR/RCR/CCR1/CCR2/CCR3、GPIOA_CRH、AFIO_MAPR、GPIOA_IDR
   （均为32位原值，不截断 SWJ_CFG 等高位）与读取时刻、代次。阶段为 `IDLE`（初始化后、计数器尚未启动，
   因此 CEN=0 是正确事实）、`ZERO`（零矢量UEV刚置MOE，本次有效比较值仍为0）、
   `FIFTY`（下一UEV已装入三路900）、`STOPPED`（首次停机后）。
   `ZERO` 阶段的 CCR 标为预装值；`FIFTY` 阶段的 CCR 已在该 UEV 装入，标为非预装。
   停机阶段用“本代次真正开过 MOE”的软件标志判定，不依赖实时 MOE 位——Break 由硬件清 MOE，
   只看实时位会漏记 STOPPED。重复停机只覆盖 STOPPED 阶段，不挤占启动阶段证据。
2. **ADC IRQ 原始记录** `board/board_io.c`：`capture_irq_snapshot` 在两个 JEOC 判定之后、
   任一保护判定之前读取 TIM1 方向/CNT、TIM2 CNT、GPIOA IDR 中的 PA8/9/10 与 MOE，并在读取前后各取
   一次设备时间。`app/diag_trace.c` 的 `diag_trace_sample` 只做整数复制，不格式化、不浮点、不等待串口，
   并在 runtime 校验与保护之前调用。快照是中断读取时刻，不冒充 ADC 采样孔径时刻。
3. **分段记录**：动作代次建立前保留最近16条环形样本（`PRE`），代次建立时冻结；
   之后线性记录启动与动作样本，首次保护只冻结一次（记录触发样本在导出块中的序号）；
   停机后只再收8条恢复样本（`POST`）即关闭窗口，之后不再新增。停机时把记录阶段推进到 `STOPPED`，
   因此恢复样本一定标为停机段，不会被当成 50% 动作数据。持续故障不能清空或覆盖首次证据。
   导出开始时在临界区内一次锁存条数与完成/溢出标志，并停止接收新样本，保证头帧与末帧口径一致。
4. **导出**：全部在停机后由前台按固定顺序发出，每帧仍是 `<前缀>,<8位hex>…,<CRC4>\r\n`
   （CCITT-FALSE，覆盖末CRC之前含最后逗号）：`P1T0` 头帧（格式版本、动作前/动作/总条数、
   完成与溢出标志、冻结标志、首次故障序号、首条序号、冻结原因与序号、配置快照数、代次）、
   每个阶段 `P1T2`（控制寄存器）/`P1T3`（PSC/ARR/RCR/CCR）/`P1T4`（CRH/MAPR/IDR/MOE/预装标志）、
   `P1T1` 逐条样本（序号、完成/读前/读后时间、原始U/V、编码器角、TIM1 CNT、TIM2 CNT、
   引脚与MOE、标志、方向、阶段）、`P1T5` 末帧（实际条数、头帧条数、分段条数、完成与溢出）。
   既有 `P1D0`/`P1E1`/`P1D1` 布局与发送顺序不变，原始记录块排在其后。
5. **完整性判定** `tools/dq_report.py` 的 `trace_reports`/`read_trace`：强制 头帧→配置三连→样本→末帧
   的顺序、逐条 index 连续、序号递增且完成时间间隔有界、分段计数与末帧一致；缺帧、重复、错序、
   CRC 失败都抛错且不补齐。恢复窗口未收满或溢出只记标志并如实返回 `complete=0`。

### 本批验证

- 主机注入（`tools/test_dq_current.py` + `tests/m1/test_dq_current.cpp`）：正常20ms截止、原始U越限、
  原始V越限、STOP、Break、启动在首个UEV被配置检查拒绝（破坏RCR）、采样停止 共七条终止路径各导出一个块。
  前五条要求 `complete=1`、恢复窗8条齐全且阶段 0/1/2/3 完整（Break 也必须留下 STOPPED 快照）；
  故障样本序号指向正确样本且该样本原始值等于注入值；启动被拒路径只有阶段 0/3、无动作样本，
  恢复样本必须标为 STOPPED 且三路引脚低、MOE=0；采样停止路径在12ms超时后导出 `complete=0`，
  之后恢复的采样不得改变已锁存条数。
- 负例：篡改CRC、删一帧、相邻帧换序、把 `P1T0` 的格式版本改成2 都被解析器拒绝；
  “arm之后、动作代次建立之前就失败”的尝试不得导出任何 `P1T` 帧。
- 实际 Keil 工程重建（固件 `01-00-03`，构建 2026-11-01 00:03）：`Code=48428 RO-data=756 RW-data=16
  ZI-data=15236`，0 error，1 warning 为厂家 `stm32f1xx_hal_adc_ex.c` 既有括号警告不变。
  同一源清单经 `tools/build_m1.py` 命令行重建为 `Code=48436 RO=756 RW=16 ZI=15236`；
  两套构建同源、RO/RW/ZI 相同，Code 差8字节（链接路径与对齐差异），不是逐字节一致。
- `tools/check_dq_stack.py`：RW_IRAM1 13204B（≤0x4800），保留栈 2048B，静态组合 1852B；
  ADC1_2_IRQHandler 栈深度 288→400B。记录新增约 2500B ZI，只在 `BOARD_DQ_VECTOR_DIAGNOSTIC`
  构建中分配。
- `tools/verify_m1.py` 全绿：工程/清单一致、35个C源文件加startup的源闭包、编译器依赖记录、
  厂商47个文件哈希、UTF-8/换行/空白与134个相对链接。
- 门控覆盖调用点：非诊断构建不分配记录RAM（同一单元 `.bss` 2528→0 字节），
  ADC中断不取引脚/定时器快照，`board_pwm` 的阶段快照编译为空表达式，也不输出 `P1T` 帧。
- 未做：板端时序、ADC IRQ 新增路径的实际耗时、功率端波形与示波器对照。记录新增成本未实测，
  不能把主机模型或静态栈分析当作板上时序证据；本批仍是 `accepted=false`。

### 已知限制

- 采样相位仍为225us；本批**不**提供相位对照或自动轮换，避免在同一固件里未经标识和分次触发就改变触发链路。
  若后续需要对照，必须显式标识、分次触发，且故障后不自动继续输出。
- 引脚快照只表明该瞬间 PA8/9/10 逻辑电平；边沿附近（方向变化或读取跨度>2us）标记为不确定，
  不能据此判定不同步。
- 记录不改变保护：记录失败、串口忙或导出不完整都不延长输出或重开MOE。
- `board_prepare_pulse` 在启动校验阶段被拒的路径，在本固件里由 `output_inputs_are_valid()`
  在更早处拦截，实际不可达；代码仍保留“启动已发起”标志以便该路径出现时记录停机配置快照，
  但它没有对应的主机可达用例，不能算已覆盖。
- 主机夹具的 `GPIOA->IDR` 不随 `BRR` 写入变化，所以样本 `pins` 字段在主机上恒为0；
  “停机样本三路为低”的解析规则在主机只验证了不许为高，没有验证真实引脚驱动。
- `MDK-ARM/m1_sampling.uvprojx` 已用 `tools/generate_m1_mdk.py` 从源清单重新生成，恢复
  `--check` 一致性；本次只比上一提交多一条 `diag_trace.c`。之前工作区里的 Keil 重存版本
  （含 `Utilities/Flash2`、`SFDFile`、`DebugOption` 等 IDE 默认字段）已另存为
  `build/dq_current/uvprojx_keil_resave_20261031.xml` 备查。下载器与调试设置实际保存在未跟踪的
  `.uvoptx`，生成器不写这些字段；若日后在 Keil 内再次保存工程，`--check` 会再次失败，
  需要单独决定是否让生成器纳管下载配置。

## 同固件两相位对照（01-13-07）

普通Reset选择低电平中心，串口显示DQ_VEC0_LOW225。按住PA12，按下并松开Reset，再松开PA12，选择高电平中心DQ_VEC0_HIGH250。两次都等READY_PRESS_PA12后再按下并松开PA12一次。选择动作只在双ADC启动前读取；每次复位重新采集512组静态零点，两个相位分别保留整段输出到P1T5。若看到INVALID或未到READY，不进入实验。

P1T0版本2末字段（CRC之前）为TIM2 CCR2启动阶段读回的微秒数，225或250。P1T2的IDLE配置采集早于相位选择。解析器继续读取版本1；没有相位证据时返回phase_consistent=null。版本2以有效且未标记跨边沿的50%阶段IRQ样本复核TIM2计数是否位于所选触发点后的12us窗口，迟到/无样本应单列，不能直接判为物理不同步。两种采样理想距开关边沿均12.5us，SSI仍在175us启动。板端未运行。
