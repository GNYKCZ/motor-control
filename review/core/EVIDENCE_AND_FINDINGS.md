# 契约、证据与 Finding

“应当怎样”来自用户要求、当前 Issue 和适用契约；“实际怎样”来自可执行路径、配置、日志和运行结果。实现和测试不能反向覆盖需求；注释/命名不能替代事实。需求未定时记录假设/缺口，不能凭经验把建议升级为验收。

确认 Finding 必须同时有：范围归属、具体位置和证据、可达触发条件、现实影响、已排除最可能保护条件的验证。证据不足项进入 Residual risks，不混进缺陷清单。

每个Finding还须说明与当前工作包验收的关系、为何必须本批修复；优先关注阻塞主线成果的关键路径。
确认会导致错误控制、输出/停机异常、数据结论失真、构建不可用或违背必要契约的问题仍阻塞交付。
风格、一般文档措辞、未使用未来能力或可选完善，没有确认影响时记建议/follow-up，不升级阻塞；
若措辞本身造成错误操作/错误结论等真实影响，仍按同一证据门槛判定，不能一律豁免文档或测试缺陷。
证据真实性与关键测试假阳性不能因赶主线而忽略；不以进度目标压低缺陷优先级，不设置任意时间配额。

- P0：有明确可达证据的非预期驱动/保护失效等严重后果，或普遍数据破坏。
- P1：核心闭环、时序、数学/物理或主要结论错误。
- P2：现实工况下的边界、状态、复现性或测试假阳性问题。
- P3：影响较小的客观错误。

Confidence 记录 0–1 的主观证据充分性；至少 0.80 才列确认问题，0.80–0.89 还须影响明确。它不是校准概率，高分不能补足缺失证据。去重按根因处理，使用稳定 RV-001 等 ID。

缺少硬件实测本身不是“发现硬件故障”；如果当前验收要求实测，则是未满足的验收/验证缺口。既不凭猜测报错，也不因看不到硬件就宣称安全。
